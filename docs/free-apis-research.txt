================================================================================
FREE APIs: HOW TO FIND THEM, HOW TO VET THEM, AND WHAT IS ACTUALLY FREE
Research notes for Applyocalypse
================================================================================

Last researched: 2026-09-01 (sources read 2026-08-31 to 2026-09-01)

WARNING ON FRESHNESS
    Free-tier limits change faster than any document can track. Between
    Dec 2025 and Aug 2026 alone: GitHub Models was retired entirely,
    Clearbit's free Logo API was shut down, Gemini's free daily quota was
    cut (and sources still disagree on the new number by 6x), and Crunchbase
    removed its free tier. Treat every number below as "was true when read,
    at the URL given". Re-verify anything you are about to depend on, in the
    provider's own console, before you ship it.

    Numbers marked "unverified" could not be confirmed from an official
    source. They are NOT guesses. Do not treat them as real.


================================================================================
1. HOW TO FIND FREE APIS
================================================================================

This is the durable part. Tools rot; method does not.

--------------------------------------------------------------------------------
1.1  THE DIRECTORIES (start here, but do not stop here)
--------------------------------------------------------------------------------

  public-apis/public-apis (GitHub)
      https://github.com/public-apis/public-apis
      ~474k stars. 48 categories (including a "Jobs" category). Table columns
      are API | Description | Auth | HTTPS | CORS. Roughly 1,000-1,500 entries.
      Manually curated, now sponsored by APILayer, so the top of the README is
      an ad. No liveness checking: many entries are years-dead. Use it for
      DISCOVERY of what exists, never as evidence that something still works.

  APIs.guru
      https://apis.guru/  |  machine-readable: https://api.apis.guru/v2/list.json
      "Wikipedia for Web APIs." Indexes OpenAPI/Swagger specs, not marketing
      pages. As of this research: 2,529 APIs, 3,992 specs, 108,837 endpoints,
      166 unreachable, 688 invalid. The metrics endpoint
      (https://api.apis.guru/v2/metrics.json) is itself a free API. Best
      directory when you want a machine-readable contract rather than a link.

  FreePublicAPIs.com
      https://freepublicapis.com/
      659 APIs, and crucially it HEALTH-CHECKS THEM DAILY and publishes a
      health score plus a "dead" tag. That liveness signal is what public-apis
      lacks. Smaller list, higher trust per entry. Has /tags/dead, which is a
      genuinely useful page to read before you adopt anything.

  Postman Public API Network
      https://www.postman.com/explore
      Largest by raw count (Postman markets "250M+" but that counts
      workspaces and collections, not distinct APIs; third parties peg
      distinct public APIs at 100,000+). The real value is the "verified
      publisher" badge and ready-to-run collections, so you can test auth in
      30 seconds instead of reading docs.

  RapidAPI Hub
      https://rapidapi.com/
      Marketplace, not a directory. Free tiers exist but are usually tiny and
      RapidAPI marks up the paid tiers. Note their own distinction: "free"
      APIs need no card, "freemium" APIs REQUIRE a card on file for overages.
      JSearch (see section 4) is the job-relevant example.

  apilist.fun
      https://apilist.fun/
      Effectively abandoned. Footer still reads "(c) 2019". Listed here so you
      do not waste time on it.

  ProgrammableWeb
      DEAD. Confirmed. Founded 2005, acquired by MuleSoft 2013, then
      Salesforce. Shut down Oct 2022, formal announcement Feb 2023. Its
      ~19,000-API directory is gone from the live web.
      Where the corpse is: Wayback Machine snapshots of
      programmableweb.com/apis/directory, and the community archive at
      https://github.com/api-evangelist/programmableweb

  Domain-specific awesome-* lists
      Almost always better than the general directories, because they are
      maintained by people who actually use the APIs. For LLMs specifically
      see section 3.1. The pattern: search GitHub for
      "awesome <domain> api" sorted by recently-updated, not by stars. A
      3-year-old 20k-star list is worse than a 6-month-old 500-star one.

1.2  THE NON-OBVIOUS METHODS (these find things directories miss)
--------------------------------------------------------------------------------

  a) READ THE PRODUCT'S OWN DEVELOPER DOCS FIRST
      The highest-yield and most-skipped move. If you want company data, go to
      the company's site and look for /developers, /api, /docs, or a
      "Developers" footer link. Directories lag reality by 12-24 months;
      the vendor's own pricing page is the source of truth. Every single
      correction in this document came from doing this.

  b) GITHUB CODE SEARCH, AS A DISCOVERY SIGNAL ONLY
      Searching GitHub for config templates (.env.example, config.sample.yml,
      docker-compose.yml) reveals which APIs real projects actually integrate,
      including ones no directory lists. You learn that an API EXISTS and what
      its env var and base URL look like.

      >>> HARD RULE: this is for discovering that a service exists. If you
      >>> encounter a real credential that someone leaked, you do not use it.
      >>> Not once, not "just to test". Using another party's leaked key is
      >>> unauthorised access, it bills or rate-limits an innocent third
      >>> party, and it will get your app's behaviour attributed to them.
      >>> The correct action on finding a live leaked key is to notify the
      >>> repo owner or the provider, and move on. Go sign up for your own.

  c) SEARCH THE PRICING LANGUAGE, NOT THE PRODUCT
      Query patterns that surface free tiers directories never indexed:
          "<domain> api" "free tier" -"credit card"
          "<domain> api" "no credit card required"
          "<domain> api" "forever free" OR "free forever"
          site:news.ycombinator.com "<domain> api" free
      Inverting it also works: search for the paid competitor's name plus
      "alternative" plus "free" to find the scrappy challenger.

  d) WAYBACK MACHINE FOR VANISHED OR SHRUNKEN FREE TIERS
      https://web.archive.org/web/*/<pricing-url>
      Two uses. First, archaeology: recover docs for a service whose free tier
      was killed (this is the only way to read the old ProgrammableWeb or the
      pre-shutdown Clearbit docs). Second, and more useful, TREND DETECTION:
      diff a provider's pricing page across 2-3 years. A free tier that went
      10,000/mo -> 1,000/mo -> 100/mo is telling you exactly what happens next.
      Do this before you build on any free tier you plan to keep for years.

  e) GOVERNMENT AND UNIVERSITY OPEN-DATA PORTALS
      Systematically underused. No key or a trivial key, no commercial-use
      ban, public-domain or CC licensing, and institutional funding means they
      do not vanish when a founder loses interest. This is the single most
      durable category of free API there is.
          https://catalog.data.gov/        US federal, ~556,000 datasets
          https://data.europa.eu/          EU, search API at /api/hub/search/
          https://www.bls.gov/developers/  US labour statistics (see 4.4)
          https://services.onetcenter.org/ US occupation taxonomy (see 4.4)
          https://data.sec.gov/            US company filings (see 5.1)
      Also: national statistics offices, city open-data portals, and
      university library APIs.

  f) READING A COMPETITOR'S NETWORK TRAFFIC FOR UNDOCUMENTED ENDPOINTS
      Open DevTools, filter Network to Fetch/XHR, perform the action, and read
      the JSON the site's own frontend calls. This finds per-company endpoints
      that are genuinely public but undocumented. It is how people discovered
      the ATS job-board endpoints in section 4.3, which are officially
      documented but only lightly advertised.

      >>> LEGAL / TOS CAVEAT, READ THIS BEFORE YOU USE IT:
      >>> The endpoint responding does not mean you are authorised.
      >>> - US case law (hiQ v. LinkedIn 2019; Meta v. Bright Data 2024) has
      >>>   narrowed the CFAA so that scraping data visible to a logged-OUT
      >>>   anonymous user, without bypassing a technical access control, is
      >>>   generally not a computer-crime violation.
      >>> - But that is criminal law only. Terms of service are CONTRACT law
      >>>   and still bind you. Clickwrap terms (you clicked "I agree") are
      >>>   materially more enforceable than a browsewrap footer link.
      >>> - The moment you log in to reach an endpoint you have almost
      >>>   certainly accepted clickwrap terms AND moved into
      >>>   authorised-access territory. That is the worst combination.
      >>> - EU courts have gone further than US ones (the CJEU let Ryanair
      >>>   contractually restrict API/site use).
      >>> Practical line for this project: logged-out, non-personal, factual
      >>> data, at a polite rate, with an honest User-Agent, is low risk.
      >>> Anything behind a login, anything personal, or anything that
      >>> requires defeating a rate limit or CAPTCHA is not worth it.
      >>> When an official API exists, use the official API.

  g) LOOK AT WHO ALREADY SOLVED IT
      Search GitHub for open-source projects in your problem space and read
      their dependency list and integration directory. For this project, the
      ATS-aggregator repos in section 4.3 are worth more than any directory.


================================================================================
2. HOW TO VET A FREE API BEFORE DEPENDING ON IT
================================================================================

Run this before writing the first line of client code. Roughly 10 minutes,
and it will save you a rewrite.

  [ ] 1. IS IT ALIVE?
         Last commit / changelog / blog post date. A docs site with no
         changelog entry in 18 months is a warning. Check the status page
         (status.<vendor>.com) and whether it has any history at all: a
         status page that has never recorded an incident is usually a status
         page nobody updates.

  [ ] 2. WHO PAYS FOR IT?
         The single most predictive question. Rank by durability:
           government / statutory mandate  > very durable
           the API is the product (paid tiers fund the free tier) > durable
           big-co loss leader / developer funnel > can be killed at any time
                                                   (GitHub Models, Clearbit)
           venture-subsidised land grab > will re-price on schedule
           one person's hobby project on a free Heroku-alike > will vanish
         If you cannot name who pays the bandwidth bill, assume it disappears.

  [ ] 3. AUTH MODEL
         None > static API key > app_id+key > OAuth. Fewer moving parts is
         better in a desktop app, where you cannot hide a secret and cannot
         easily run an OAuth redirect. If auth requires a server-side secret,
         a local-first app has an architecture problem, not an API problem.

  [ ] 4. THE ACTUAL RATE LIMIT, IN THE UNITS THAT MATTER
         Get requests/second AND requests/day AND requests/month. Providers
         quote whichever flatters them. A "1,000 req/hour" limit with a
         200 req/MONTH cap (see JSearch) is a 200 req/month API. Also check:
         is the limit per key, per IP, per organisation, or global? Creating
         extra accounts to multiply a global limit is against every ToS and
         usually detected.

  [ ] 5. COMMERCIAL USE, IN WRITING
         Read the ToS, not the pricing page. Search the terms text for:
         "commercial", "redistribut", "resell", "aggregat", "attribution",
         "non-commercial", "evaluation", "trial". This is where free tiers
         actually bite (see section 8.2). If it is ambiguous, email them and
         KEEP THE REPLY.

  [ ] 6. ATTRIBUTION AND LINK-BACK OBLIGATIONS
         Several free tiers are free only if you display a credit or a
         followed backlink (RemoteOK, Remotive, logo.dev, O*NET, OSM). That
         is a UI requirement, which means it is a product decision, which
         means find out now and not after the design is locked.

  [ ] 7. DATA / PRIVACY TERMS
         Does the provider train on, log, or human-review what you send?
         For this app that is a gating question, not a footnote. See 8.3.

  [ ] 8. DOES IT DEGRADE GRACEFULLY?
         Can the feature ship without it? If the honest answer is no, either
         pay for it, self-host it, or drop the feature. See 8.5.

  [ ] 9. SNAPSHOT THE EVIDENCE
         Save the pricing/ToS page to the Wayback Machine the day you adopt
         it, and note the date in code near the client. When the terms change
         under you, you will want to know what you agreed to.

3. FREE LLM / AI APIS
================================================================================

Most volatile category in this document. Model names below were current at
the research date and will be stale within months.

--------------------------------------------------------------------------------
3.1  THE DURABLE ANSWER: TRACK THE COMMUNITY LISTS, NOT THIS TABLE
--------------------------------------------------------------------------------

These are auto-updated far more often than any hand-written doc. Read these
first, every time.

  cheahjs/free-llm-api-resources
      https://github.com/cheahjs/free-llm-api-resources
      ~29k stars. Partly auto-generated from provider APIs, so the per-model
      rate-limit tables are unusually current. Splits "free providers" from
      "providers with trial credits", which is the distinction that matters.
      THIS IS THE SINGLE BEST SOURCE. Most numbers in 3.2 come from here.

  mnfst/awesome-free-llm-apis
      https://github.com/mnfst/awesome-free-llm-apis
      ~7k stars, created Mar 2026, CC0. Narrower scope: PERMANENT free tiers
      only, no trial credits. Adds context window and max output columns,
      which cheahjs's list mostly omits. Good cross-check.

  Note: these two disagree on Gemini's daily limit by roughly 75x. That
  disagreement is itself the finding. See 3.2.

================================================================================
4. JOB AND CAREER DATA APIS
================================================================================

--------------------------------------------------------------------------------
4.1  THE TWO EVERYONE ASKS ABOUT FIRST, ANSWERED: BOTH ARE CLOSED
--------------------------------------------------------------------------------

  INDEED      The public Publisher API is SHUT DOWN. New signups were rolled
              back Oct 2022 and the XML feed was retired (2023-2024,
              sources vary). indeed.com/publisher no longer resolves. What
              remains: an iframe-only hosted search widget (no data access),
              and an NDA-gated enterprise data partnership. The partner APIs
              that do exist (Indeed Apply, Sponsored Jobs) are for ATSs and
              staffing platforms and NONE of them returns job postings.
              Even when alive, its terms were display-only: storing listings
              or using them for analytics was prohibited.

  LINKEDIN    There is NO public jobs-read API and there never will be one
              for an app like this. All API access has required Partner
              Program membership since 2015. Job data sits in the Talent API,
              which is invitation-only to certified ATS/enterprise HR vendors.
              LinkedIn explicitly REJECTS use cases including "job search
              automation", scraping, and profile aggregation. Reported
              partnership costs run $10k-50k+/year.

  Conclusion: any job-data feature must be built on aggregators (4.2), on
  per-company ATS boards (4.3), or on government sources (4.4).

--------------------------------------------------------------------------------
4.2  AGGREGATORS AND JOB BOARDS
--------------------------------------------------------------------------------

4.3  PER-COMPANY ATS JOB-BOARD APIS  <-- MOST RELEVANT TO THIS PROJECT
--------------------------------------------------------------------------------

This is the highest-value section for Applyocalypse. These are free, need no
key, and return exactly the jobs you are about to fill a form for. The app
already has ATS adapters, so the same board token identifies both the listing
source and the filling strategy.

HOW THEY WORK
    Each is a single-tenant public read endpoint keyed by the company's own
    board slug. There is NO enumeration or lookup endpoint on ANY of them:
    you must already know the slug, which you extract from the company's
    careers-page URL.
        Greenhouse   boards.greenhouse.io/{token}      or
                     job-boards.greenhouse.io/{token}
        Lever        jobs.lever.co/{site}
        Ashby        jobs.ashbyhq.com/{name}
    None of the three publishes a numeric rate limit for its public read
    endpoint. Self-throttle and cache.

  NAME             Greenhouse Job Board API
  DOCS             https://docs.greenhouse.io/job-board.html
  BASE             https://boards-api.greenhouse.io/v1/boards/{board_token}
  AUTH             NONE for all GETs. Quoted: "Job Board data is publicly
                   available, so authentication is not required." Only the
                   application-submission POST needs Basic auth with a key.
  FREE LIMIT       None documented anywhere.
  COMMERCIAL       Not addressed; data is the company's own public postings.
  RETURNS          title, location.name, absolute_url (application URL),
                   updated_at, requisition_id, departments, offices.
                   With ?content=true: full HTML description (entity-escaped).
                   With ?questions=true on a single job: STRUCTURED CUSTOM
                   QUESTIONS (label, required, fields[] with name/type/values;
                   supports file upload, text, textarea, single/multi select),
                   plus optional EEOC compliance and demographic_questions
                   blocks, plus pay_input_ranges.
  WORTH IT?        YES, HIGHEST VALUE ITEM IN THIS DOCUMENT FOR THIS APP.
                   The ?questions=true payload is a machine-readable schema of
                   the exact form the worker is about to fill, INCLUDING the
                   EEOC/demographic fields that safety invariant #2 requires
                   be flagged requires_review. You can pre-plan a fill, and
                   pre-flag EEO questions, before opening a browser at all.

  NAME             Lever Postings API
  DOCS             https://github.com/lever/postings-api
  BASE             https://api.lever.co/v0/postings/{site}
  AUTH             None for reads (JSON/HTML/iframe/XML modes). The
                   application POST uses ?key=APIKEY and is limited to
                   ~2 requests/second.
  FREE LIMIT       Read side undocumented.
  COMMERCIAL       Not addressed. Note many customers disable the public feed.
  RETURNS          title, categories (team/department/location/commitment/
                   level), hostedUrl, applyUrl, description, optional salary.
                   NO custom-question schema is exposed.
  WORTH IT?        Yes for listings and metadata. Leanest of the three; you
                   still have to discover the form fields in the browser.

  NAME             Ashby Public Job Posting API
  DOCS             https://developers.ashbyhq.com/docs/public-job-posting-api
  BASE             https://api.ashbyhq.com/posting-api/job-board/{jobBoardName}
  AUTH             None shown for this endpoint.
  FREE LIMIT       Not documented for the public endpoint.
  COMMERCIAL       Not addressed.
  RETURNS          title, location + secondaryLocations[] with structured
                   address, department, team, isRemote, workplaceType
                   (OnSite/Remote/Hybrid), descriptionHtml AND
                   descriptionPlain, employmentType, publishedAt, jobUrl,
                   applyUrl, isListed. With ?includeCompensation=true a
                   structured compensation object (tier summaries, min/max,
                   currency, interval). NO question schema.
  WORTH IT?        Yes. Best structured metadata of the three (plain-text
                   description is a gift for JD analysis; compensation is
                   structured). Stops at applyUrl.

  ALSO PUBLIC, NO KEY:
    Workable    GET https://apply.workable.com/api/v1/widget/accounts/{account}
                add ?details=true for full descriptions. No key. Limits
                unverified.
    Personio    GET https://{company}.jobs.personio.de/xml?language=en
                XML, no auth. Always alphabetical, not configurable.
                Limits unverified.

  KEY OR PLAN DEPENDENT:
    SmartRecruiters  https://api.smartrecruiters.com/v1/companies/{id}/postings
                     API key or OAuth2 (internal_postings_read); many
                     customers leave it effectively open, so auth is
                     inconsistent across companies. Better query/filter
                     support than Lever or Ashby. Limits unverified.
    Recruitee        https://{company}.recruitee.com/api/offers/
                     Help centre now says the Careers Site API requires a
                     token; older docs said public. Treat as token-required.
                     Rate limiting reportedly introduced Oct 2025, number
                     unverified. Docs flagged "work in progress".
    Teamtailor       https://api.teamtailor.com/v1/jobs
                     Requires X-Api-Key + X-Api-Version even to read one
                     company. Aggregation needs a manual partner deal
                     (techpartnerships@teamtailor.com). Most locked down.

  FINDING BOARD TOKENS AT SCALE
    Since none of the ATSes offer enumeration, the community solved it by
    maintaining lists. Most useful:
        https://github.com/Feashliaa/job-board-aggregator
            Claims 1,000,000+ positions from 20,000+ companies across
            Greenhouse, Lever, Ashby, Workday, BambooHR, iCIMS, Paylocity.
            Daily refresh via GitHub Actions. The data/*_companies.json files
            are effectively an off-the-shelf token directory.
            Note their per-ATS concurrency tuning as a politeness reference:
            50 Workday, 30 Greenhouse/Lever/iCIMS, 10 BambooHR,
            5 Ashby/Paylocity.
        https://github.com/plibither8/jobber
            Small normalisation layer over Ashby/Greenhouse/Lever/BambooHR.
            Good shape to copy for a unified internal model.
        https://github.com/adgramigna/job-board-scraper
            Greenhouse/Lever/Ashby/Rippling, normalised, daily.
    Simplest first-party method: when the user pastes a job URL, parse the
    slug out of it. You get the token for free, from the user, with no list
    to maintain. Do that before you import anyone's JSON.

6.1  DOCUMENT CONVERSION (DOCX / PDF)  <-- directly relevant to this app
--------------------------------------------------------------------------------

  The short version: for a local-first desktop app that already mutates DOCX
  and TEX on disk, DO NOT send the user's resume to a conversion API. Both
  hosted options below are small, and one of them explicitly forbids
  production use. The local options are better on every axis including
  privacy. This is the same argument as 8.3, applied to file conversion.

  NAME             Gotenberg  (self-hosted)
  DOCS             https://gotenberg.dev/
  AUTH             None. Docker container you run.
  FREE LIMIT       None. MIT licensed.
  COMMERCIAL       Yes, unrestricted (MIT).
  WORTH IT?        Yes, if you want a service boundary. Bundles Chromium
                   (HTML/Markdown/URL to PDF) and LibreOffice (Word/Excel/
                   PowerPoint and 100+ formats to PDF) plus merge, split,
                   encrypt, watermark, PDF/A and Factur-X, with no host
                   dependencies to install. One `docker run` and it works.
                   Heavier than needed if you only convert DOCX to PDF.

  NAME             LibreOffice headless  (local process)
  DOCS             soffice --headless --convert-to pdf file.docx
  AUTH             None.
  FREE LIMIT       None. MPL 2.0.
  COMMERCIAL       Yes.
  WORTH IT?        Yes, and it is the simplest correct answer for this app.
                   No network call, no key, no quota, no data leaving the
                   machine, and it matches the existing local-first document
                   pipeline. The cost is bundling or detecting a LibreOffice
                   install, which is a packaging problem, not an API problem.

  NAME             CloudConvert
  DOCS             https://cloudconvert.com/pricing
  AUTH             API key, no card required
  FREE LIMIT       Verified: 10 credits/day, daily reset, no rollover.
                   ~1 credit = 1 minute of conversion; general = 1 credit,
                   Office to PDF = 2, PDF to Office = 4. Max 1GB file,
                   5 min processing, 5 concurrent tasks, low priority queue.
  COMMERCIAL       Not explicitly banned, but the tier is positioned "for
                   personal use, testing and hobby projects"; SLA, DPA and
                   team billing are paid-only. For a product handling
                   resumes, the absence of a free-tier DPA matters.
  WORTH IT?        No, for this app. Roughly 5 resume conversions a day
                   across ALL users of a shared key, and no DPA.

  NAME             ConvertAPI
  DOCS             https://www.convertapi.com/pricing  |  /terms
  AUTH             API token, no card required
  FREE LIMIT       250 conversions, ONE-TIME on signup, not monthly.
                   (Third-party listings say the trial expires after 30 days;
                   that was NOT confirmed in ConvertAPI's own terms text.)
  COMMERCIAL       NO. Their ToS states the free trial "is only offered for
                   testing and development purposes, and shall not be used
                   for any other purposes."
  WORTH IT?        No. Explicitly not licensed for production by its own ToS.

--------------------------------------------------------------------------------
7.1  THE STATE OF PLAY: THE TWO OBVIOUS ANSWERS ARE BOTH CLOSED
--------------------------------------------------------------------------------

  BING WEB SEARCH API
      RETIRED 11 AUGUST 2025, announced mid-May 2025. Confirmed on
      Microsoft's own lifecycle page: "Any existing instances of Bing Search
      APIs will be decommissioned completely, and the product will no longer
      be available to be used or new customer signup."
      The retirement covered the ENTIRE family at once: Web, Image, Video,
      News, Entity, Autosuggest, Spell Check, Visual Search, Custom Search.
      Endpoints now return HTTP 410 Gone.
      Microsoft's replacement is "Grounding with Bing Search" inside Azure AI
      Agents ($14 per 1,000 transactions). It is NOT a drop-in: it returns
      LLM-generated grounded answers rather than raw structured results, and
      requires Azure AI Agent infrastructure.

  GOOGLE PROGRAMMABLE SEARCH / CUSTOM SEARCH JSON API
      CLOSED TO NEW CUSTOMERS. Google's own docs (last updated 2026-02-18)
      state the API "is closed to new customers", and existing customers have
      until 1 JANUARY 2027 to migrate. New GCP projects get a 403
      PERMISSION_DENIED even after complete setup. The historic free tier was
      100 queries/day then $5 per 1,000 up to 10,000/day.
      Google points to Vertex AI Search, which is an enterprise product, not
      a drop-in replacement.
      ==> Do not build on this. It will not accept your signup and it sunsets
          inside 16 months.

  Consequence: every remaining option is either a paid SERP proxy with credits,
  a self-hosted metasearcher, or a narrow special-purpose endpoint. There is no
  longer a general-purpose, free, no-card web search API.

8. CAVEATS, TOS TRAPS AND PRIVACY WARNINGS
================================================================================

--------------------------------------------------------------------------------
8.1  RATE-LIMIT PATTERNS
--------------------------------------------------------------------------------

  * READ ALL THE DIMENSIONS. Providers advertise the flattering one. JSearch
    quotes "1,000 requests/hour" next to a 200 requests/MONTH cap. Groq's
    1,000 RPD looks generous until you notice the 8,000 TPM ceiling that
    actually binds on long documents. Always find the tightest dimension.

  * THE LIMIT IS USUALLY GLOBAL, NOT PER KEY. OpenRouter says it plainly:
    "we govern capacity globally", so extra accounts do not multiply it.
    Groq enforces at ORGANISATION level. Google enforces per PROJECT, not
    per key.

  * EXPONENTIAL BACKOFF WITH JITTER, ALWAYS. On 429, honour Retry-After when
    present (Groq sends it only on 429s). Retrying immediately on a daily-cap
    429 just burns quota. Distinguish a per-minute 429 (retry) from a
    per-day 429 (stop until reset, and tell the user).

  * KNOW WHEN THE DAY RESETS. Google resets at midnight Pacific. Cloudflare
    resets at 00:00 UTC. If you schedule background work, do not schedule it
    right before a reset boundary.

  * CACHE AGGRESSIVELY, AND PERSIST THE CACHE. This app already has SQLite.
    A job posting fetched from an ATS board does not change minute to minute;
    Jobicy explicitly delays 6 hours and Remotive 24 hours, so polling faster
    than that gains you nothing but a ban.

  * SELF-THROTTLE WHERE NO LIMIT IS PUBLISHED. "No documented rate limit" is
    not "no rate limit". It means the limit is undocumented and enforcement is
    at their discretion. The Greenhouse/Lever/Ashby endpoints are all in this
    category. A sane default: 1-2 req/s per host, serial per company.

--------------------------------------------------------------------------------
8.2  KEY ROTATION ETHICS  (short section, firm line)
--------------------------------------------------------------------------------

  DO NOT rotate keys to defeat a rate limit. Creating multiple accounts to
  multiply a free quota violates essentially every ToS in this document,
  is explicitly called out by OpenRouter and Groq, is detectable, and ends
  with the provider killing the free tier for everyone. cheahjs's list opens
  with exactly this plea: "Please don't abuse these services, else we might
  lose them."

  DO NOT use a credential you found rather than one you were issued. Leaked
  keys in public repos are a discovery signal that an API exists (see 1.2b),
  never a credential. Using one is unauthorised access and bills a stranger.

  LEGITIMATE rotation, all of which is fine:
    - The USER supplies their own key for their own account. This is the
      correct model for a local-first desktop app, and it is what this app
      already does for LLM providers in Settings.
    - Failing over between DIFFERENT providers when one is exhausted.
    - Rotating your own key on a schedule for security hygiene.

8.3  PRIVACY: THE ONE THAT ACTUALLY MATTERS FOR THIS APP
--------------------------------------------------------------------------------

  >>> READ THIS BEFORE WIRING ANY FREE LLM TIER INTO THE TAILORING PATH. <<<

  A resume is one of the densest packets of personal data a person owns:
  full legal name, home address, phone, personal email, complete employment
  history, education, and often enough to infer age, nationality, and
  immigration status. A cover letter frequently adds health, caring
  responsibilities, or reasons for leaving a job. Applyocalypse also handles
  EEO and criminal-history answers.

  Sending that to a free LLM tier is, in the general case, sending it to be
  trained on and read by strangers.

  THE EXPLICIT CASE, quoted from Google's Gemini API Additional Terms:

      "Google uses the content you submit to the Services and any generated
       responses to provide, improve, and develop Google products and
       services and machine learning technologies."   [Unpaid Services]

      "human reviewers may read, annotate, and process your API input and
       output"

      "Do not submit sensitive, confidential, or personal information to the
       Unpaid Services."                               [Google's own bold]

      "You may use only Paid Services when making API Clients available to
       users in the European Economic Area, Switzerland, or the United
       Kingdom."

  Read those four together. Google is telling you, in its own terms, that
  the free tier is not for personal data, and that you may not serve EU, UK
  or Swiss users on it at all. A resume is personal data. This is not a grey
  area, and "the user consented" does not fix it if the user is in the EEA,
  because the restriction there is on YOU, not on them.

  Note the geographic nuance in Google's favour: for users located in the
  EEA, Switzerland or the UK, Google applies PAID-tier data handling even to
  free quota. But the prohibition on serving EEA/CH/UK users via free
  Services stands regardless.

  OTHER PROVIDERS, SAME SHAPE:
    Mistral       Free-mode prompts may be used to train Mistral models
                  UNLESS YOU OPT OUT. Default is opt-in to training on the
                  free tier. Verify the toggle before sending anything real.
    OpenRouter    Separate free/paid toggles for "providers that may train".
                  If you refuse training, OpenRouter will not route to
                  training providers, which shrinks or empties the free pool.
                  In effect, the free models are free because of the data.
    Kilo Gateway  "All free models may use your prompts for training."
    OpenCode Zen  "Free models may use data for improvement."
    NVIDIA NIM    Serving real end-users is not permitted without a paid
                  enterprise licence, so the question does not arise.
    Groq          Notably clean: API Customer Data is carved out of the
                  privacy policy and governed by a Services Agreement and
                  DPA (processor terms). No free-vs-paid training split
                  found. This is the exception, not the rule.

  THE RULE TO ENCODE IN THE PRODUCT:
    1. NEVER send resume, cover-letter, or profile content to a free tier
       that trains on input. Not by default, not opportunistically, not
       "just for the fast JD-analysis path" if the JD prompt carries any
       profile context.
    2. If a free tier is offered at all, it must be an explicit, informed,
       per-provider user choice with the training language shown verbatim,
       not buried in a settings tooltip. The user is consenting to Google
       training on their resume. Say that, in those words.
    3. Segment by sensitivity. Public JD text is not personal data; sending
       a scraped job description to a free tier is defensible. Sending the
       user's resume is not. If the codebase cannot cleanly distinguish
       those two paths, it cannot safely use a free tier at all.
    4. For EEA/UK/CH users, do not use Google's free tier. This is a
       jurisdiction check, not a preference.
    5. Prefer local inference for anything touching the profile. See 9.
    6. This is also true of NON-LLM APIs. Do not send a user's email address
       to a free verification API without disclosure; you have just told a
       third party that this person exists and is job hunting.

  SECONDARY LEAK, EASY TO MISS: query patterns are data. Repeatedly asking a
  free company-enrichment API about "Acme Corp" from one IP tells that vendor
  someone is applying to Acme. Aggregated, that is a saleable signal about a
  named individual's job search. A local-first product should care about that.

--------------------------------------------------------------------------------
8.5  DESIGNING SO A VANISHED FREE API DEGRADES GRACEFULLY
--------------------------------------------------------------------------------

  Assume every free API in this document will, within 24 months, either
  disappear, add a card requirement, or cut its quota by 10x. GitHub Models
  and Clearbit both did exactly this inside the last 12 months. Design for it.

  1. ONE ADAPTER INTERFACE PER CAPABILITY, NOT PER VENDOR.
     The capability is "enrich a company", not "call Clearbit". The app
     already does this correctly for ATS adapters; use the same shape.
     A vendor should be deletable in one file.

  2. EVERY ENRICHMENT IS OPTIONAL BY CONSTRUCTION.
     If the company-logo call fails, the application still submits. Model
     enrichment as a nullable column populated by a background job, never as
     a precondition in the apply path. Ask of each integration: "if this
     returns 500 forever starting tomorrow, what breaks?" If the answer is
     "the core flow", it is not an enrichment, it is a dependency, and a free
     tier is the wrong place for it.

  3. NEVER LET A THIRD PARTY BLOCK THE USER.
     Hard timeouts (2-5s), a circuit breaker that opens after N consecutive
     failures and stays open for minutes, and a UI that shows the feature as
     unavailable rather than spinning. A local-first app that hangs on a
     dead API has thrown away its main advantage.

  4. CACHE FOREVER, EXPIRE LAZILY.
     Persist every response in SQLite with a fetched_at. When the API dies,
     the cache is now your dataset and the feature degrades to "slightly
     stale" instead of "gone". This is the single highest-leverage mitigation
     and it costs almost nothing.

  5. HAVE A NAMED FALLBACK CHAIN, AND TEST IT.
     For each capability write down primary -> secondary -> local -> none.
     Then actually run with the primary disabled, in CI if possible. An
     untested fallback is not a fallback.

  6. HEALTH-CHECK AND SURFACE IT.
     A lightweight periodic probe per provider, with the result visible in
     Settings. When a user reports "company info stopped working", you want
     to already know it was the vendor.

  7. VERSION AND DATE YOUR ASSUMPTIONS IN CODE.
     A comment near each client with the limit, the ToS date, and the URL you
     read. When it breaks in 18 months, that comment is the whole
     investigation.

  8. PREFER THE DURABLE TIER WHEN THE QUALITY GAP IS SMALL.
     Government APIs and local inference do not get acquired. Where a
     government source is 80% as good as a startup's, take the government
     source. See the shortlist.

  9. USER-SUPPLIED KEYS ARE A FEATURE, NOT A COMPROMISE.
     This app already stores LLM keys via safeStorage. Extending that pattern
     to other providers means quota is the user's, ToS is between them and
     the vendor, and the app ships no shared secret. For a local-first
     desktop product this is the correct default for anything metered.

9. RECOMMENDED SHORTLIST FOR APPLYOCALYPSE SPECIFICALLY
================================================================================

What I would actually wire up, in priority order, and why.

TIER 1: WIRE THESE UP. High value, free, durable, no privacy problem.

  1. GREENHOUSE JOB BOARD API  (+ Lever, + Ashby)
     https://boards-api.greenhouse.io/v1/boards/{token}/jobs?questions=true
     WHY: This is the best single find for this codebase. No auth, no key,
     no quota, and Greenhouse returns a MACHINE-READABLE SCHEMA OF THE EXACT
     FORM the worker is about to fill, including field types, required flags,
     select options, file-upload fields, and separately-labelled EEOC and
     demographic question blocks.
     Concretely: you can pre-plan a fill and pre-flag every EEO question as
     requires_review BEFORE launching a browser, which is a direct, cheap
     reinforcement of safety invariant #2 rather than a detection heuristic
     applied to rendered DOM. You can also detect an unfillable posting
     early. The app already has per-ATS adapters, so the board slug is a key
     you can derive from the job URL the user already pastes: no list to
     maintain, no scraping, no ToS question.
     Add Lever and Ashby for listing metadata (Ashby's descriptionPlain and
     structured compensation are notably good for JD analysis).

  2. LOCAL INFERENCE VIA OLLAMA, AS THE DEFAULT FOR PROFILE-TOUCHING WORK
     https://ollama.com/
     WHY: It is the only option in this document with zero cost, zero rate
     limit, zero ToS risk, zero vendor mortality AND zero data exposure. For
     a local-first, privacy-focused product, running resume tailoring against
     a local model is not a budget compromise, it is the product thesis.
     Section 8.3 is the argument: every mainstream free LLM tier either
     trains on input, requires opting out of training, or forbids the use.
     Local has none of those problems. Position hosted providers as an opt-in
     quality upgrade with the training terms shown verbatim, and keep local
     as the default for anything containing the user's data.

  3. SEC EDGAR + WIKIDATA + UK COMPANIES HOUSE  (company research)
     https://data.sec.gov/ | wikidata.org | developer.company-information...
     WHY: The company-research feature is exactly where a startup free tier
     would betray you, and it is exactly where government data is strongest.
     Free, no commercial-use restriction, generous limits (10 req/s, 600 per
     5 min), public-domain or CC0 licensing, and institutionally funded so
     they will outlive the app. Covers filings, financials, officers,
     founding date, industry, HQ. Add the still-free Clearbit Autocomplete
     API (600 req/min, no key) purely to resolve a typed company name to a
     domain, which is the awkward first step everything else depends on.

  4. O*NET WEB SERVICES  (job-title and skills normalisation)
     https://services.onetcenter.org/
     WHY: 50,000 requests/day free, exact and documented, and it gives you a
     stable occupational vocabulary to normalise wildly inconsistent job
     titles and to map JD requirements to a canonical skills taxonomy. That
     makes tailoring and matching measurably better without an LLM call.
     Watch the ToS clause about registration-gated or paid apps if
     Applyocalypse ever grows a paid tier.

TIER 2: WORTH ADDING, WITH CONDITIONS.

  5. JOBICY (+ REMOTIVE, + REMOTEOK)  (job discovery)
     WHY: Jobicy is the only free job feed found with an EXPLICIT, broad
     commercial grant naming "AI products" and "internal applications" as
     permitted uses. No key, 200 jobs/request. Remotive and RemoteOK extend
     coverage cheaply. All three cost a visible attribution link, which is
     a small, honest price. Note RemoteOK requires a DOFOLLOW link
     specifically.
     Skip Adzuna and JSearch for shipping: Adzuna's free key is a 14-day
     commercial trial and JSearch is 200 requests/month.

  6. GROQ, AS THE HOSTED LLM FALLBACK  (not the default)
     WHY: Of the hosted free tiers, Groq has the cleanest data posture:
     API Customer Data sits under a Services Agreement and DPA rather than
     being swept into product improvement, and no free-vs-paid training
     split was found. Combined with 1,000 RPD and the fastest inference
     available, it is the right hosted fallback when local inference is
     unavailable or too slow. Mind the 8,000 TPM ceiling: chunk long
     documents rather than sending a whole resume in one prompt.
     Pair with OpenRouter as the abstraction layer so swapping providers is
     a config change, not a rewrite. Note OpenRouter's own free models are
     only 50 req/day until a one-time $10 credit purchase raises it to
     1,000/day, which is the best value-per-dollar on this page.

  7. HUNTER.IO OR REOON  (contact finding / email verification)
     WHY: If the app verifies a recruiter email, Hunter's 50 credits/month
     covers both finding and verification with the clearest terms; Reoon's
     600/month is the most generous pure-verification allowance.
     BUT FIRST: do syntax + MX + disposable-domain checking LOCALLY (see the
     self-hosted list in 5.2). It is free, instant, leaks nothing, and
     catches most bad addresses. Only escalate to an API for the residual,
     and disclose it. Also note SMTP-probe accuracy against Gmail/Outlook/
     Yahoo has degraded badly across all vendors, so the marginal value of
     the paid check is lower than it looks.

  8. LOCAL DOCUMENT TOOLING INSTEAD OF A CONVERSION OR OCR API
     Tesseract (Apache 2.0) + LibreOffice headless (MPL 2.0), or Gotenberg
     (MIT) if you want a service boundary.
     WHY: The hosted alternatives are both small and legally awkward.
     CloudConvert gives 10 credits/DAY shared across every user of a shared
     key, with no DPA on the free tier. ConvertAPI's own terms forbid
     production use outright. And both mean uploading the user's resume, the
     exact thing section 8.3 says not to do. Local tooling has no quota, no
     key, no ToS, and no data exposure. The only cost is packaging, which is
     a problem this app already solves for the Python worker.
     Keep OCR.space (25,000 req/month, explicitly commercial-friendly) as the
     documented fallback for scans that Tesseract handles badly, gated behind
     the same disclosure as any other upload.

  9. FRANKFURTER, IF SALARIES EVER NEED NORMALISING ACROSS CURRENCIES
     https://frankfurter.dev/
     WHY: No key, no quota, explicit commercial permission, no attribution,
     84 central-bank sources, self-hostable. It is the single cleanest free
     API in this document and it costs nothing to adopt. Only wire it up if
     the multi-country job feeds in 4.2 actually surface foreign salaries.

DELIBERATELY NOT RECOMMENDED

  Google Gemini free tier   Best free model, but its own terms say do not
                            submit personal information and forbid serving
                            EEA/UK/CH users on free Services. Disqualifying
                            for the tailoring path. Fine for public JD text
                            only, if you can guarantee no profile context
                            leaks into that prompt.
  NVIDIA NIM                Serving real end-users needs a paid enterprise
                            licence.
  OpenCorporates            Free tier bans commercial use outright.
  Crunchbase                No free tier exists.
  Adzuna / JSearch / Jooble Trial windows and micro-quotas, not tiers.
  Indeed / LinkedIn         Closed. Do not plan around them at any price
                            you would pay.
  GitHub Models             Retired July 2026. Delete any reference.
  Bing Search API           Retired August 2025, entire family, HTTP 410.
  Google Custom Search      Closed to new customers; full sunset Jan 1 2027.
  Brave Search API          Free plan removed Feb 2026; card now mandatory.
  restcountries v3.1        Keyless endpoint gone; v5 needs a key. Any code
                            still calling v3.1 is silently broken.
  WorldTimeAPI              Sunset. Use a local tz library.
  CloudConvert/ConvertAPI   See shortlist item 8. Use local tooling.
  Z AI / Chutes             Unclear terms and, for Z AI, a China-hosted
                            endpoint receiving resume content.

ONE ARCHITECTURAL NOTE
  Everything above metered belongs behind the existing user-supplied-key
  pattern (safeStorage-encrypted in SQLite settings, handed to the worker
  via the 0600 temp file, never via child-process env). Shipping a shared
  key in a desktop binary means shipping a secret to every user and pooling
  every user's quota into one bucket that the first heavy user exhausts.
  User-supplied keys also put the ToS relationship between the user and the
  vendor, which is where several of the restrictions in 8.4 stop mattering.
